
# 1. Zero-shot vs Few-shot

## Zero-shot

예시 없이 모델에게 작업을 지시하는 방식이다.

### 장점

- 가장 간단하다.
- 토큰 사용량이 적다.
- 대부분의 일반적인 작업에서 충분한 성능을 낸다.

### 단점

다음과 같은 경우에는 결과가 흔들릴 수 있다.

- 분류 기준이 모호한 경우
- 출력 형식이 중요한 경우

---

## Few-shot

예시를 함께 제공하여 모델이 기준을 학습하도록 하는 방식이다.

설명보다 실제 예시를 보여주는 것이 더 효과적이다.

### 장점

- 분류 기준이 명확해진다.
- 출력 형식 준수율이 높아진다.
- 결과의 일관성이 향상된다.

### Few-shot 설계 원칙

- 예시는 2~5개 정도가 적절하다.
- 경계선 사례를 포함한다.
- 라벨 분포를 균형 있게 구성한다.
- 출력 형식도 예시로 함께 제공한다.

### 주의사항

- 특정 라벨에 편향된 예시를 넣지 않는다.
- 평가셋과 예시를 중복하지 않는다.
- 너무 많은 예시는 비용만 증가시키고 효과는 크지 않다.

---

# 2. Chain of Thought (CoT)

## 개념

모델이 최종 답을 내기 전에 사고 과정을 단계적으로 작성하도록 하는 기법이다.

```text
문제

↓

변수 정리

↓

계산 과정

↓

최종 답
```

---

## 장점

- 계산 정확도가 향상된다.
- 논리적 추론이 쉬워진다.
- 오류가 발생한 위치를 확인할 수 있다.
- 검증이 가능하다.

---

## 적합한 작업

- 계산
- 논리 문제
- 복잡한 추론
- 단계별 분석

---

# 3. Self-Consistency

## 개념

같은 문제를 여러 번 독립적으로 해결한 후 가장 많이 나온 답을 선택하는 방법이다.

```text
질문

↓

모델 실행 × N

↓

다수결

↓

최종 답
```

---

## 특징

- 비결정성을 활용한다.
- 정확도를 높일 수 있다.
- 실행 비용은 실행 횟수만큼 증가한다.

---

## 적합한 작업

- 금융 계산
- 규정 해석
- 정확성이 중요한 업무

---

# 4. ReAct (Reasoning + Acting)

## 개념

생각(Reasoning)과 행동(Action)을 반복하며 문제를 해결하는 방식이다.

AI Agent의 핵심 동작 원리이다.

```text
Thought

↓

Action

↓

Observation

↓

Thought

↓

Answer
```

---

## 동작 과정

### Thought

현재 필요한 정보를 판단한다.

### Action

필요한 도구(API, 검색 등)를 호출한다.

### Observation

도구 결과를 확인한다.

### Answer

관찰한 결과를 기반으로 최종 답변을 생성한다.

---

## 장점

- 외부 데이터를 활용할 수 있다.
- 환각(Hallucination)을 줄일 수 있다.
- 실제 업무 자동화에 적합하다.

---

## 핵심 원칙

모르는 것은 추측하지 않고 반드시 도구를 통해 확인한다.

---

# 5. Tree of Thought (ToT)

## 개념

하나의 사고 흐름이 아닌 여러 가지 해결 방법을 탐색한 후 가장 적합한 방법을 선택하는 기법이다.

```text
문제

├── 방법 A
├── 방법 B
└── 방법 C

↓

비교

↓

최적안 선택
```

---

## 특징

- 다양한 접근 방식을 비교할 수 있다.
- 정답이 없는 문제에 적합하다.

---

## 활용 분야

- 전략 수립
- 시스템 설계
- 기획
- 아이디어 탐색

---

# 6. 프롬프트 기법 선택 기준

| 상황 | 추천 기법 |
|------|-----------|
| 단순 작업 | Zero-shot |
| 기준이 모호한 분류 | Few-shot |
| 계산 및 논리 | CoT |
| 외부 정보 필요 | ReAct |
| 다양한 해결책 탐색 | Tree of Thought |

# 7. 시스템 프롬프트와 사용자 프롬프트

## 시스템 프롬프트(System Prompt)

항상 유지되는 규칙을 정의하는 프롬프트이다.

### 포함 내용

- 역할(Role)
- 규칙
- 출력 형식
- 금지사항
- 판단 기준

---

## 사용자 프롬프트(User Prompt)

매 요청마다 변경되는 실제 입력 데이터이다.

### 포함 내용

- 사용자 질문
- 입력 데이터
- 처리 대상 정보

---

## 역할 비교

| 시스템 프롬프트 | 사용자 프롬프트 |
|----------------|----------------|
| 변하지 않는 규칙 | 매번 변경되는 입력 |
| 역할 정의 | 데이터 전달 |
| 출력 형식 정의 | 실제 요청 |

---

## 설계 원칙

```text
System Prompt → 규칙

User Prompt → 데이터
```

자동화에서는 시스템 프롬프트와 사용자 프롬프트를 분리하는 것이 중요하다.

---

# 실습 - 음식 배달 리뷰 분류 시스템

이번 실습에서는 음식 배달 리뷰를 자동으로 분석하는 AI를 설계하였다.

시스템 프롬프트를 이용하여 AI의 역할과 규칙을 정의하고, 항상 동일한 JSON 형식으로 결과를 출력하도록 구성하였다.

## 시스템 프롬프트

```text
너는 음식 배달 서비스의 리뷰를 분리하는 CX팀의 10년차 직원이야.

# 임무
입력된 배달 리뷰 1건을 분석해 지정된 JSON 형식으로만 응답한다.

# 분류 기준
- category: 한식 / 중식 / 양식 / 일식 / 기타 중 하나
- sentiment: 긍정 / 부정
  - 긍정: 만족, 칭찬, 재주문 의사
  - 부정: 불만, 항의, 개선 요청
- rating: 별점 1 ~ 5점
  - 5: 매우 만족, 강한 칭찬, 재주문 의사 표현
  - 4: 전반적으로 만족, 사소한 아쉬움
  - 3: 장단점이 비슷하거나 특별한 감정 없음
  - 2: 불만이 있으나 일부는 괜찮음
  - 1: 매우 불만, 강한 불평, 환불·재주문 거부 수준
- summary: 30자 이내 요약

# 규칙
- JSON 외의 텍스트를 절대 출력하지 않는다.
- rating은 리뷰의 전체적인 만족도를 기준으로 판단한다.
- 리뷰에 없는 내용을 추측하지 않는다.
- summary는 핵심 내용만 간결하게 작성한다.

# 출력 예시
{
  "category":"한식",
  "sentiment":"긍정",
  "rating":5,
  "summary":"음식이 맛있고 재주문 의사 있음"
}
```

---

## 시스템 프롬프트 설계 포인트

### 1. 역할(Role) 정의

AI에게 **음식 배달 서비스 CX팀의 10년차 직원**이라는 역할을 부여하여 리뷰를 고객센터 담당자의 관점에서 분석하도록 하였다.

---

### 2. 명확한 임무(Task) 정의

AI의 역할을 리뷰 분석으로 한정하고, JSON 형식으로만 응답하도록 지정하였다.

---

### 3. 세부 분류 기준 정의

리뷰를 다음 기준으로 분석하도록 정의하였다.

- 음식 종류(category)
- 감성(sentiment)
- 만족도(rating)
- 요약(summary)

특히 rating은 각 점수의 의미를 함께 정의하여 일관된 판단이 가능하도록 하였다.

---

### 4. 출력 형식 고정

JSON만 출력하도록 규칙을 지정하였다.

예시

```json
{
  "category": "한식",
  "sentiment": "긍정",
  "rating": 5,
  "summary": "음식이 맛있고 재주문 의사 있음"
}
```

---

### 5. Guardrail(제약 조건)

모델의 불필요한 추측이나 출력 오류를 방지하기 위해 다음과 같은 규칙을 정의하였다.

- JSON 외 출력 금지
- 리뷰에 없는 내용 추측 금지
- 전체 만족도를 기준으로 rating 판단
- summary는 핵심만 간결하게 작성

---

## 실습을 통해 배운 점

- 시스템 프롬프트는 AI의 역할과 규칙을 정의한다.
- 판단 기준을 구체적으로 작성할수록 응답의 일관성이 높아진다.
- JSON 출력 형식을 고정하면 자동화 시스템에서 활용하기 쉽다.
- Guardrail을 통해 환각(Hallucination)을 줄이고 출력 품질을 높일 수 있다.

# 9. 프롬프트 평가

프롬프트는 감이 아니라 평가를 통해 개선해야 한다.

## 평가 절차

```text
평가셋 작성

↓

프롬프트 실행

↓

결과 비교

↓

실패 원인 분석

↓

프롬프트 수정

↓

재평가
```

---

## 평가 방법

### 정확 일치(Exact Match)

출력 결과와 정답이 동일한지 비교한다.

적합한 작업

- 분류
- 정보 추출

---

### 체크리스트 평가

형식과 규칙 준수 여부를 평가한다.

예시

- JSON 형식 준수
- 금지어 포함 여부
- 필수 항목 존재 여부

---

### LLM-as-Judge

다른 LLM을 심판으로 활용하여 결과를 평가하는 방법이다.

대량 평가에 적합하지만 사람의 기준과 비교하여 신뢰성을 검증해야 한다.

# 11. 컨텍스트 엔지니어링

## 개념

컨텍스트 엔지니어링(Context Engineering)은 모델이 작업을 수행하는 순간에 **필요한 정보를 선별하여 적절한 형태와 순서로 제공하는 것**이다.

프롬프트뿐만 아니라 다음과 같은 정보가 모두 컨텍스트에 포함될 수 있다.

- 시스템 규칙과 사용자 요청
- 이전 대화와 현재 작업 상태
- 검색한 문서와 데이터베이스 조회 결과
- 코드, 로그, 오류 메시지
- 도구 실행 결과와 메모리

## 필요한 이유

모델의 컨텍스트 공간은 제한되어 있다. 정보를 너무 적게 주면 중요한 조건을 놓치고, 너무 많이 주면 핵심 정보가 묻히거나 오래된 내용을 기준으로 판단할 수 있다.

따라서 모든 정보를 한꺼번에 넣는 것보다 **현재 단계에 필요한 정보만 제공하는 것**이 중요하다.

## 설계 원칙

- 관련성 높은 정보만 선택한다.
- 중요한 규칙과 목표를 명확하게 구분한다.
- 긴 문서는 요약이나 목차를 먼저 제공하고 필요할 때 원문을 찾게 한다.
- 오래된 정보와 중복 정보를 제거한다.
- 진행 상태는 문서나 데이터베이스에 기록하여 다음 작업에서 다시 사용할 수 있게 한다.
- 도구의 출력은 모델이 이해하기 쉬운 구조로 전달한다.

## 예시

코드 오류를 수정하는 Agent라면 전체 저장소를 모두 전달하는 대신 다음 정보를 제공한다.

```text
작업 목표
+ 관련 소스 코드
+ 오류 로그
+ 프로젝트 규칙
+ 실행할 테스트 명령
```

# 12. 하네스 엔지니어링

## 개념

하네스 엔지니어링(Harness Engineering)은 AI 모델이 실제 작업을 안정적으로 수행하도록 **모델을 둘러싼 실행 환경과 제어 장치 전체를 설계하는 것**이다.

모델이 두뇌라면 하네스는 모델이 보고, 행동하고, 결과를 확인할 수 있게 만드는 작업 환경이다.

## 주요 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| 도구 | 파일, 검색, API, 터미널 등을 사용하게 함 |
| 권한과 격리 | 접근 범위를 제한하고 위험한 작업을 통제함 |
| 컨텍스트 관리 | 작업에 필요한 문서와 상태를 제공함 |
| 검증 장치 | 테스트, 린터, 평가 기준으로 결과를 확인함 |
| 상태 관리 | 진행 상황, 결정, 실패 내용을 기록함 |
| 복구 절차 | 재시도, 체크포인트, 롤백을 지원함 |
| 관찰 가능성 | 로그, 비용, 실행 시간을 추적함 |

## 설계 원칙

- Agent가 사용할 수 있는 도구와 권한을 명확히 제한한다.
- 성공 조건을 테스트나 평가 기준으로 확인할 수 있게 한다.
- 긴 작업은 작은 단계로 나누고 진행 상태를 남긴다.
- 실패 횟수, 시간, 비용의 한도를 정한다.
- 중요한 변경이나 되돌리기 어려운 작업에는 사람의 승인을 요구한다.
- 반복되는 오류는 규칙, 테스트 또는 도구로 예방한다.

## 예시

코딩 Agent를 위한 하네스는 다음과 같이 구성할 수 있다.

```text
저장소 규칙 + 코드 검색 도구 + 편집 권한
               ↓
          Agent 작업
               ↓
테스트 + 린터 + 코드 리뷰 + 실패 시 재시도
```

# 13. 프롬프트·컨텍스트·하네스 엔지니어링 비교

| 구분 | 핵심 질문 | 주요 대상 |
| --- | --- | --- |
| 프롬프트 엔지니어링 | 어떻게 지시할 것인가? | 역할, 명령, 예시, 출력 형식 |
| 컨텍스트 엔지니어링 | 지금 어떤 정보를 보여줄 것인가? | 문서, 대화, 상태, 검색 결과 |
| 하네스 엔지니어링 | 어떤 환경에서 행동하고 검증할 것인가? | 도구, 권한, 테스트, 로그, 복구 절차 |

세 개념은 서로 대체하는 관계가 아니다. 좋은 프롬프트로 목표를 전달하고, 필요한 컨텍스트를 제공하며, 하네스로 실행과 검증을 통제할 때 Agent의 결과가 더 안정적이 된다.

여러 Agent의 작업 순서와 반복 구조는 [AI Agent 오케스트레이션과 루프 엔지니어링](./ai_agent_orchestration.md)에서 이어서 다룬다.
